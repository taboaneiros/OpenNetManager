# ADR-0001 — Arquitetura em Camadas

## Context

O OpenNetManager precisa separar claramente responsabilidades de apresentação, aplicação, persistência, integração remota e parsing. O domínio envolve múltiplos vendors, coleta via SSH e evolução incremental, o que torna arriscado concentrar lógica em views ou models ativos.

## Decision

Adotar arquitetura em camadas explícitas com o fluxo obrigatório:

View → Service → Repository → Driver → SSH → Parser → Domain Objects

Cada camada terá responsabilidades restritas e contratos claros.

## Consequences

### Positivas

- menor acoplamento;
- melhor testabilidade;
- maior previsibilidade na expansão multi-vendor;
- redução de vazamento de infraestrutura para UI.

### Negativas

- mais arquivos e classes desde o início;
- maior disciplina necessária para contribuições;
- curva inicial de onboarding um pouco maior para quem espera Django “tradicional”.

## Alternatives

### Colocar lógica em views/models Django

Mais rápido no curto prazo, porém inadequado para parsing, SSH e múltiplos vendors.

### Microsserviços desde o início

Escalaria separação física, mas introduziria complexidade operacional prematura para a Fase 0.
